# 多目标驻留池：真实 DLL 测试记录

2026-11-19 对固定旧版基线与当前优化版使用同一批三 DLL 样本进行了单独对照，包含冷分析、驻留切回、磁盘恢复和内存成本；详见[三 DLL 旧版对照报告](real-baseline-comparison-20261119.md)。本页后续记录保留各次原有测试条件。

2026-11-18，在 Windows 11 x64、i9-13900HX、约 39.8 GiB 内存、Node 24.22.3、Ghidra 12.1.4、JDK 21 上，用本仓库 `207302bc184780d863b0eed60fe18a3c34590c33` 基础上的多目标驻留池工作区代码测试。使用真实 MCP 调用，未改变全局 REA 配置。实验目录和缓存与用户原有 Checkpoint 隔离。

两个用户 DLL `vl3vpn.dll`、`ArrayVPNApi.dll`，以及三个从 Windows 系统目录复制的 DLL 构成五个不同目标。每个场景分别以一个新 REA 会话执行两轮目标切换和单函数反编译；前三个和前四个目标分别用于容量 3、4，五个目标用于容量 5 和默认容量 2 的对照。第二轮每个目标的伪代码 `normalized_result` 摘要与事先取得的参考摘要一致；这只验证选定函数，不证明全部分析结果等价。

所有目标均先有隔离的 Checkpoint，测试期间操作系统缓存为热状态；目标 1 的证据确认恢复已有 Program、未重新运行自动分析。时间包括每次 `open_binary` 和 `procedure_pseudo_code` 调用，不包含调用之间的脚本开销。默认容量 2 与容量 5 使用相同的五目标、同一套测试脚本和顺序；两者各测一次，不能据此推断统计稳定性。

默认容量 2 和容量 5 的完整场景墙钟时间分别为 196.074 和 97.843 秒，包含启动、两轮调用、采样等待和关闭；对应进程家族 CPU 采样增量下界约 224.08 和 106.39 秒。容量 3、4 的完整场景分别为 76.072、97.293 秒，CPU 采样增量下界约 86.61、104.66 秒。这些值包含实验驱动进程；短命进程或采样前后的 CPU 会被低估。没有测量模型 token，不能据此声称 token 改善。

内存是按约两秒间隔采样进程家族并求和；工作集可能重复计入共享页且受 Windows 回收影响，私有提交不是物理驻留量，短时峰值可能漏采。容量是每个 REA 会话的目标数量上限，不是内存上限；更大或不同类型的 DLL 可能占用更多。按顺序单次运行，不能作为跨机器的内存预算或速度保证。

四次会话关闭均返回成功，记录的四个 MCP 进程 PID 在实验结束后未见存活。详细 MCP 计时、证据和采样留在本机 `reports/multi-dll-research-20261118-212455/`；这些文件包含样本路径及分析结果，分享前应审查。最初为准备 Checkpoint 的独立多进程预试验曾误选外部导入符号而失败，修正后完成；该失败记录仍保存在同一目录，不计入上表。

## 自动模式的六目标验证（后续工作区修改）

在同一台机器、同一测试工作区和隔离 Checkpoint 下，另行验证 `REA_GHIDRA_RETAINED_TARGETS=auto`。使用上述五个 DLL，加上复制的 Windows `aclui.dll`；前五个使用已有 Checkpoint，第六个需要冷分析。单个真实 REA MCP 会话依次分析六个目标，再按相同顺序切回并反编译。采样观察到最多六个 Ghidra Java 进程同时存在；第二轮六次“打开＋反编译”分别为 0.186、0.192、0.160、0.185、0.290、0.732 秒，总计 1.745 秒；选定函数的结果摘要前后一致。

全流程墙钟时间为 192.6 秒（包括第六个目标的首次分析和关闭），进程家族 CPU 采样增量下界约 270.3 秒，采样最大工作集之和 3,346 MiB、私有提交之和 3,238 MiB。采样期间系统最低可用物理内存约 7.55 GiB，没有达到 90% 内存占用阈值；内存压力、30 分钟闲置、回收失败及恢复的边界由可控测试验证，而非通过耗尽主机内存或等待 30 分钟验证。关闭调用报告成功；采样中记录的 REA MCP 与 Java 进程 PID 在检查时没有存活。不能据此证明所有系统资源均已释放。

实验输出仍保存在本机 `reports/multi-dll-research-20261118-212455/`（`adaptive-result.json` 和 `adaptive-samples.ndjson`）；上述内存、时间及正确性验证的局限同前，不代表其他文件或机器上的保证。

## Codex 客户端隔离验证（2026-11-18）

使用本机 Codex CLI 0.166.0-alpha.5.1 的 `codex exec` 启动独立 MCP 进程，配置指向从当前仓库全新克隆并构建的优化版，并显式设置 `REA_GHIDRA_RETAINED_TARGETS=auto` 和独立 Checkpoint 目录。它依次通过 MCP 打开并反编译 `vl3vpn.dll`、`ArrayVPNApi.dll`、Windows 样本副本 `acppage.dll`，再切回第一个 DLL 并反编译，最后调用 `close_binary`；这些调用均成功。

第一个目标使用隔离目录中的已有 Checkpoint，返回的 Evidence 明确说明已恢复 Program 且没有重新执行自动分析；另外两个目标首次分析后保存了 Checkpoint。切回第一个目标前，进程采样观察到同一 REA 服务下同时存在三个 Ghidra Java 进程，首次恢复时的 Java 进程也在其中；切回后的 Evidence ID 与首次一致。期间采样到的整机物理内存最高占用约 80.6%，低于 90% 触发线，不能据此声称实机验证了高内存回收。关闭后，采样记录到的三个 Java 进程和 REA MCP 进程均已退出。

本次还运行了 `BinarySessionRetainedSwitch.test.ts` 和 `config.test.ts`，共 125 项通过；其中 90% 边界、模拟内存压力、30 分钟闲置、失败清理与租约行为为受控测试，并非实机耗尽内存或等待 30 分钟的结果。Codex CLI 的客户端测试与桌面应用当前会话区分：当时桌面会话仍连接到更新前启动的旧 REA 进程，需要重新连接或重启客户端才能确保加载更新后的代码和配置。

实验输出保存在本机隔离目录，包括 Codex 事件记录及进程采样；其中可能包含本机路径和分析结果，分享前应审查。此测试只覆盖所列 DLL 和选定函数，不代表全部目标或其他客户端均已验证。
