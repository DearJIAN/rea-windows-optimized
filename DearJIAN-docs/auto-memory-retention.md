# auto 自动模式：内存驱动的 Ghidra 会话保留

这篇笔记记录本仓库 Windows Ghidra Checkpoint 工作流的 `auto` 模式：它怎样决定保留和释放目标、与固定容量有何区别、由哪些文件实现，以及目前验证了什么。使用入口见[根目录 README](../README.md#auto-自动模式与默认值)，Checkpoint 基础及原版对照见[优化原理笔记](windows-checkpoint-optimization.md)。

## 本机配置和项目默认值

项目本身在没有设置 `REA_GHIDRA_RETAINED_TARGETS` 时，默认最多同时保留 **2 个**目标（当前目标计入其中）；也可以显式设置为 `2`、`3`、`4` 或 `5`。设置为 `auto` 后，不以这些数字限制驻留数量，而是按下面的规则管理后台会话。

2026-11-18，作者本机的 Windows **用户级环境变量**与 Codex 的 REA MCP 服务环境均配置了 `REA_GHIDRA_RETAINED_TARGETS=auto`。这是该用户的部署状态，不表示克隆仓库的其他用户也自动启用了它。环境由进程启动时读取：已运行的旧 REA 服务不会因为文件或配置更新而变成新服务；Codex 需要重新连接或重启，新进程才读取 Codex 的设置。其他客户端也需要启动时继承更新后的环境，或在各自的 REA 服务环境中配置 `auto`。

## 从提问到按需保留

1. 用户提出任务，AI 选择用户授权的文件并请求 REA 打开和分析；REA **不会自行扫描、选择或预先分析**其他文件。
2. 对符合条件的 Windows 只读 Ghidra Checkpoint 会话，REA 启动 Ghidra 并处理当前目标。满足条件的已有 Checkpoint 可以恢复完成的自动分析；第一次分析仍需完成自动分析。
3. AI 根据任务请求切换到另一个目标时，REA 会检查目标、配置、租约和内存状态。允许保留时，上一个已加载会话留在后台；没有预先创建一组空闲的 Ghidra。
4. 切回后台目标时，REA 检查目标路径、内容、分析配置及会话健康状态；符合条件才复用。目标已经释放或不再适用时，按正常打开流程重新加载，并在 Checkpoint 有效时恢复磁盘结果。

## 触发规则

| 情况                                   | auto 的行为                                                                                                          |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 内存读数正常，整机物理内存占用低于 90% | 符合条件的后台目标可继续按需保留，没有固定目标数量上限。                                                             |
| 整机物理内存占用达到或超过 90%         | 在目标切换时检查；存在后台会话时，定期检查并优先释放最久未使用的后台目标。                                           |
| 后台目标闲置达到 30 分钟               | 定期检查后释放该后台目标，即使内存未达到压力线。闲置时间从该目标转入后台开始计算，重新使用并再次转入后台后重新计时。 |
| 内存读数不可用或无效                   | 不把未知当作内存充足；后续目标保留保守回退到总容量 2，仍按规则处理已到期的后台目标。                                 |
| 内存恢复充足                           | 不主动扫描或重新启动目标；下次用户任务触发打开时，再按需保留。                                                       |

内存百分比是**整台电脑的物理内存占用**：用系统报告的总物理内存和可用物理内存计算 `(总量 − 可用量) / 总量`。可用量小于或等于总量的 10% 时视为达到 90% 压力线；它不是只计算 REA 的进程内存，也不是磁盘或虚拟内存百分比。

后台目标存在时约每 **30 秒**检查一次。后台维护不会主动关闭当前目标，也不会中断正在进行的分析；如果已有请求或切换正在进行，会等待后续检查。用户自己要求切换目标时，原当前目标仍可能在切换过程中正常关闭。采样、系统分配和进程清理存在延迟，因此 **90% 是触发回收的参考线，不是系统内存的硬上限**；Ghidra 启动后也可能在下一次检查前继续增长。

## 租约、关闭和恢复

每个受管理的 Checkpoint 会话持有相应独占租约。不同路径如果对应同一 Checkpoint 键，不能同时持有该租约；REA 必须先释放冲突会话，再打开另一个路径。达到压力线后按最久未使用的顺序释放后台客户端，释放成功才视作资源清理完成；这不会删除磁盘上的 Checkpoint 或修改原 DLL。

如果后台关闭失败，REA 保留该清理的所有权，不会假装资源已经释放；下一次目标切换或显式关闭时会重试。自动回收不会中断当前请求或替用户关闭其他程序。磁盘 Checkpoint 不可用、配置变化、目标内容变化等情况，仍按各自的现有验证和错误处理规则执行。

## 实现涉及哪些文件

| 文件                                                                                                                                              | 负责的具体行为                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| [src/config/environment.ts](../src/config/environment.ts)、[parseConfig.ts](../src/config/parseConfig.ts)、[types.ts](../src/config/types.ts)     | 接受 `2`～`5` 与 `auto`，将启动时选择传入应用配置；其他值报配置错误。                                                              |
| [src/domain/retainedTargets.ts](../src/domain/retainedTargets.ts)                                                                                 | 定义配置类型，并把总物理内存与可用物理内存转换为正常、高压力或未知；可用量不大于 10% 为高压力。                                    |
| [src/composition/binary.ts](../src/composition/binary.ts)、[BinarySessionComposition.ts](../src/application/binary/BinarySessionComposition.ts)   | 在 Windows 的 `auto` 模式下注入系统内存读数、时钟和 30 秒检查定时器；CLI 与 MCP 共用会话组合。                                     |
| [src/application/binary/BinarySession.ts](../src/application/binary/BinarySession.ts)                                                             | 按使用顺序管理后台绑定和转入后台时间；切换时检查容量与租约，后台维护在安全边界检查压力和 30 分钟闲置，并负责关闭与失败重试。       |
| [BinarySessionRetainedSwitch.test.ts](../src/application/binary/BinarySessionRetainedSwitch.test.ts)、[src/config.test.ts](../src/config.test.ts) | 用受控时钟、内存读数和客户端覆盖超过 5 个目标、90% 边界、30 分钟闲置、进行中请求、失败清理及恢复；这些受控测试不冒充真实内存压力。 |

`auto` 的维护只作用于原本符合条件的 Windows 只读 Ghidra Checkpoint 会话，不把其他 Provider 或数据库编辑会话自动加入池中。固定容量模式保持原有数量规则；只有 `auto` 使用上述自动内存与闲置回收策略。

## 测试与限制

在正常内存条件下，本仓库构建版本及本机新启动的全局 REA 都分别测试了六个真实 DLL 的同会话驻留与切回。全局进程的第二轮六次打开和反编译合计 **1.254 秒**，选定函数结果摘要与参考一致；进程关闭报告成功。该次没有让机器达到 90% 内存占用，也没有等待真实的 30 分钟：这些边界通过受控测试验证。具体样本、采样及限制见[多目标测试记录](multi-target-pool-results.md)；本机全局测试的原始记录在本地 `reports/multi-dll-research-20261118-212455/`，分享前应检查路径和分析结果。
