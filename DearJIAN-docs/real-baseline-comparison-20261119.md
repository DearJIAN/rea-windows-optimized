# 旧版与 Windows 优化版：三 DLL 真实对照

2026-11-19 在同一台 Windows 11 x64 机器上，使用三个真实 Windows DLL 副本和 Ghidra，通过独立 REA MCP 进程比较旧版与优化版。两版依次执行 `A → B → C → A → B → C`，每次调用 `open_binary` 后以 `list_procedures` 的 `summary` 查询函数列表。两次测试均成功结束，三个目标的函数记录数分别为 382、421、246；**数量一致不代表全部函数内容均已验证等价**。

## 版本和测试条件

- 旧版是首次 Windows Checkpoint 提交的父提交 [`675287517c98c702ee88ad036c5e3b8dd4bcc7a7`](https://github.com/DearJIAN/rea-windows-optimized/commit/675287517c98c702ee88ad036c5e3b8dd4bcc7a7)，在临时隔离目录导出并构建。这是固定历史基线，并非对上游当前版本的断言。
- 优化版是本机全局安装的 REA 6.9.0；其抽查的 Ghidra provider、client 和配置解析构建文件与本仓库 [`cc196a9b33aa1067a23867a4fa869a6683efacc6`](https://github.com/DearJIAN/rea-windows-optimized/commit/cc196a9b33aa1067a23867a4fa869a6683efacc6) 一致。两版版本号相同，不能单凭版本号区分代码。
- 两边均使用 Node 24.22.3、Ghidra 12.1.4、JDK 21.0.13 和同一批文件；先测旧版、后测优化版，没有清空操作系统文件缓存。两边清除继承的 REA 环境变量；优化版显式使用 `auto` 和独立的空 Checkpoint 目录，旧版 Windows 不支持此 Checkpoint 工作流。
- 文件是系统 DLL 的测试副本，末尾附加独立标记以形成实验专用哈希；原始系统文件未修改。对照中的两版读取完全相同的副本字节。

## 时间结果

下表单位为秒，每项是对应 `open_binary` 与 `list_procedures` 两次 MCP 调用耗时之和，不包括客户端初始化、调用之间的驱动开销及最后关闭。

| 目标 | 旧版首次分析 | 优化版首次分析 | 旧版切回查询 | 优化版驻留切回查询 | 优化版关闭后从磁盘恢复 |
| ---- | -----------: | -------------: | -----------: | -----------------: | ---------------------: |
| A    |       95.213 |        103.928 |       88.857 |              0.188 |                 15.944 |
| B    |       80.991 |         84.028 |       83.413 |              0.157 |                 16.107 |
| C    |       77.083 |         74.635 |       82.274 |              1.418 |                 16.144 |
| 合计 |      253.287 |        262.591 |      254.544 |              1.763 |                 48.195 |

旧版六次调用组合计 **507.831 秒**，优化版为 **264.354 秒**，减少 243.477 秒，约 47.9%。其中首次三目标分析的优化版反而多用 9.304 秒；它还要创建 Checkpoint，但单次测试不能把差额全部归因于保存开销。三次切回合计减少约 99.3%，其中重复查询也可能利用已保留的 Evidence；不能将这组数字推广到任意未查询过的操作。

优化版关闭三个驻留进程后另行恢复各目标，上表最后一列包括重新打开和查询。每项 Evidence 均报告从已保存的 Program 恢复且没有重新运行自动分析；恢复仍需启动 Ghidra。关闭首次三目标会话的 MCP 调用在旧版和优化版分别为 0.459 秒和 0.965 秒；恢复后关闭优化版会话为 0.699 秒。

## 内存、CPU 与限制

用 psutil 按名义 0.5 秒间隔加采样开销记录 REA 服务及其子进程，不包含实验驱动和采样器。六次打开与查询对应的进程族采样峰值工作集之和，旧版为 **1,309.5 MiB**，优化版为 **2,563.0 MiB**；增加约 1,253.5 MiB（95.7%）。多个进程的工作集相加可能重复计算共享页，短时峰值也可能漏采；该数值不是独占物理内存。旧版采样未观察到三个 Java 进程同时存在，优化版观察到了三个。

六次旧版分析对应的六个 Java 进程 CPU 采样最大值之和约 **764.28 秒**；优化版六次工作流对应的前三个 Java 进程约 **381.20 秒**。这是采样下界估计，未包含 Node 和短生命周期辅助进程，不能称为完整进程族 CPU 时间。两次测试的整机物理内存占用采样峰值分别为 59.2% 和 61.4%。没有触发或实测 `auto` 的 90% 压力回收或 30 分钟闲置回收，也没有测量模型 token。

本次只有一组按顺序执行的样本；机器负载、操作系统缓存、代码差异和 Checkpoint I/O 的影响未单独拆分。结果不构成其他目标或机器上的性能保证。测试完成后两个隔离 MCP 进程及其记录到的 Ghidra 进程已退出，测试副本和专用 Checkpoint 已清理；原有全局配置、Checkpoint 缓存及桌面会话未修改。
